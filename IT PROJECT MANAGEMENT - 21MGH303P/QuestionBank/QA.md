**Q1. Discuss various cost controlling techniques used in project monitoring.**

Cost controlling techniques help keep the project within the approved budget.

Step-by-step:
1. **Earned Value Management (EVM)** – Compare Planned Value (PV), Earned Value (EV) and Actual Cost (AC).
2. **Cost Performance Index (CPI)** = EV / AC → If CPI < 1, corrective action is needed.
3. **Cost Variance (CV)** = EV – AC → Negative variance triggers control.
4. **Budget at Completion (BAC) forecasting** using Estimate at Completion (EAC = BAC / CPI).
5. **Cost Change Control System** – Formal approval for any cost change.
6. **Resource levelling and optimisation** to reduce unnecessary expenses.
7. **Regular cost audits and variance analysis** at every milestone.

These techniques ensure proactive cost control in the Unit-3 monitoring phase.

**Q2. Explain project risk management and mitigation strategies with suitable examples.**

Project risk management is a systematic process (Unit-3).

Steps:
1. **Risk Identification** – Brainstorming, checklists, SWOT.
2. **Risk Analysis** – Qualitative (probability-impact matrix) & Quantitative (Monte Carlo simulation).
3. **Risk Response Strategies (Mitigation):**
   - **Avoid** – Eliminate risk (e.g., change vendor).
   - **Mitigate** – Reduce impact (e.g., add buffer time).
   - **Transfer** – Insurance or outsourcing.
   - **Accept** – For low-impact risks.

Example: In a software project, risk of delay due to team skill gap → Mitigation: Conduct training (mitigate) or hire expert (transfer).

4. **Risk Monitoring** – Continuous tracking using risk register.

This forms the core of the RMMM plan.

**Q4. Explain how to analyze cost and schedule performance index for project monitoring.**

Cost and Schedule Performance Index (EVM – Unit-3).

Formulas:
- **CPI** = EV / AC
- **SPI** = EV / PV

Step-by-step analysis:
1. Collect PV, EV, AC at review point.
2. Calculate CPI & SPI.
3. Interpretation:
   - CPI > 1 → Under budget; CPI < 1 → Over budget.
   - SPI > 1 → Ahead of schedule; SPI < 1 → Behind schedule.
4. Forecast EAC & ETC.
5. Take corrective actions (crashing, fast-tracking, resource reallocation).

Example: CPI = 0.9 & SPI = 0.85 → Project is over budget and behind schedule → Immediate controlling techniques required.

**Q31. What is the difference between Cost Variance (CV) and Schedule Variance (SV)? Give formulas and examples.**

**Cost Variance (CV):**
- Formula: CV = EV – AC
- Measures whether the project is over or under budget.
- CV > 0 → Under budget; CV < 0 → Over budget.
- Example: EV = ₹6,00,000, AC = ₹7,00,000 → CV = –₹1,00,000 (over budget).

**Schedule Variance (SV):**
- Formula: SV = EV – PV
- Measures whether the project is ahead or behind schedule.
- SV > 0 → Ahead of schedule; SV < 0 → Behind schedule.
- Example: EV = ₹6,00,000, PV = ₹8,00,000 → SV = –₹2,00,000 (behind schedule).

Key difference: CV focuses on cost efficiency; SV focuses on time efficiency. Both are EVM metrics used in Unit-3 monitoring.

**Q32. Explain Budget at Completion (BAC), Estimate at Completion (EAC) and Estimate to Complete (ETC).**

These are EVM forecasting metrics (Unit-3):

**BAC (Budget at Completion):**
- Total planned budget for the project.
- Set during planning phase.

**EAC (Estimate at Completion):**
- Forecasted total cost when project finishes.
- Formula: EAC = BAC / CPI
- If CPI = 0.9 and BAC = ₹10,00,000 → EAC = ₹11,11,111 (project will cost more).

**ETC (Estimate to Complete):**
- Remaining cost to finish the project.
- Formula: ETC = EAC – AC
- Tells the team how much more money is needed.

These metrics enable proactive financial decision-making during monitoring.

**Q33. What is a Risk Register? Explain its components and how it is used in project monitoring.**

**Q38. Explain qualitative vs quantitative risk analysis with examples.**

Both are part of the risk analysis process (Unit-3):

**Qualitative Risk Analysis:**
- Subjective assessment using probability-impact matrix.
- Categorises risks as High, Medium, Low.
- Fast and easy to perform.
- Example: "Risk of key developer leaving" → Probability: High, Impact: High → Red zone.

**Quantitative Risk Analysis:**
- Numerical techniques to calculate risk impact.
- Methods: Expected Monetary Value (EMV), Monte Carlo Simulation, Decision Tree Analysis.
- Example: EMV = Probability × Impact = 0.4 × ₹5,00,000 = ₹2,00,000 expected loss.

Qualitative is done first to prioritise; quantitative is done for high-priority risks to get precise figures.

**Q43. Explain resource levelling and resource crashing as project controlling techniques.**

**Resource Levelling** (Unit-3):
- Technique to resolve resource conflicts by adjusting start/end dates of tasks.
- Goal: Avoid resource over-allocation without changing the project end date (if possible).
- May extend the project duration.
- Example: If two tasks need the same developer simultaneously, one is delayed.

**Resource Crashing:**
- Adding extra resources to critical path tasks to shorten project duration.
- Increases cost.
- Example: Adding two more developers to a critical module to meet the deadline.

| Feature | Resource Levelling | Resource Crashing |
|---|---|---|
| Goal | Smooth resource usage | Reduce project duration |
| Effect on cost | Minimal | Increases cost |
| Effect on duration | May increase | Decreases |

**Q44. A project has BAC = ₹20,00,000, AC = ₹12,00,000, EV = ₹10,00,000, PV = ₹14,00,000. Calculate CPI, SPI, CV, SV and EAC.**

**Calculations:**
- **CPI** = EV / AC = 10,00,000 / 12,00,000 = **0.833** (Over budget)
- **SPI** = EV / PV = 10,00,000 / 14,00,000 = **0.714** (Behind schedule)
- **CV** = EV – AC = 10,00,000 – 12,00,000 = **–₹2,00,000** (Cost overrun)
- **SV** = EV – PV = 10,00,000 – 14,00,000 = **–₹4,00,000** (Schedule delay)
- **EAC** = BAC / CPI = 20,00,000 / 0.833 = **₹24,01,200** (approx.)

**Interpretation:** Project is significantly over budget and behind schedule. Immediate corrective action required — resource crashing, scope reduction or schedule re-baselining.

**Q46. What is the difference between verification and validation in software testing?**

**Verification** (Unit-4):
- "Are we building the product right?"
- Checks whether the product conforms to specifications.
- Done through reviews, inspections, walkthroughs.
- Static testing — does not require running code.
- Example: Reviewing requirement documents, design documents.

**Validation:**
- "Are we building the right product?"
- Checks whether the product meets user needs.
- Done through actual testing (UAT, system testing).
- Dynamic testing — requires running the software.
- Example: End-user acceptance testing.

| Aspect | Verification | Validation |
|---|---|---|
| Question | Building it right? | Building the right thing? |
| Type | Static | Dynamic |
| Method | Reviews, inspections | Testing, execution |
| When | During development | After development |

10. **Simplicity** – Maximise the amount of work not done.
11. **Self-organising teams** – Best architectures emerge from self-organising teams.
12. **Regular reflection** – Team reflects and adjusts behaviour at regular intervals.

**Q49. What are the different types of project termination? Explain each.**

**Types of Project Termination** (Unit-4):
1. **Termination by Extinction** – Project is stopped because it succeeded (delivered) or failed.
   - Example: Project completed and handed over to operations.
2. **Termination by Addition** – Successful project becomes a permanent department/unit of the organisation.
   - Example: A software product team becomes a permanent business unit.
3. **Termination by Integration** – Project resources, deliverables and functions are absorbed into existing organisational units.
   - Example: New payroll system integrated into HR department.
4. **Termination by Starvation** – Project is not officially cancelled but budget is gradually cut until it stops.
   - Example: Project is de-prioritised and resources are slowly withdrawn.

**Q50. Explain the Kanban methodology and how it differs from Scrum.**

**Kanban** (Unit-4 – Agile Methodology):
- Visual workflow management method.
- Uses a Kanban board with columns: To Do → In Progress → Done.
- Work items (cards) move across columns as they progress.
- No fixed sprints — work is continuous flow.

**Differences from Scrum:**

| Feature | Kanban | Scrum |
|---|---|---|
| Iterations | No fixed sprints | Fixed sprints (1–4 weeks) |
| Roles | No defined roles | Product Owner, Scrum Master, Team |
| Change | Changes anytime | Changes between sprints |
| WIP Limit | Explicit WIP limits | Sprint commitment |
| Meetings | No mandatory meetings | Sprint ceremonies |
| Best for | Ongoing maintenance | New product development |

**Q51. Explain IT Service Management (ITSM) Lifecycle and its phases.**

**ITSM Lifecycle** (Unit-4):
- Framework for designing, delivering, managing and improving IT services.
- Based on ITIL (Information Technology Infrastructure Library).

**Five Phases:**
1. **Service Strategy** – Define service objectives, market and value.
2. **Service Design** – Design services, processes, policies and architectures.
3. **Service Transition** – Build, test and deploy services into production.
4. **Service Operation** – Day-to-day delivery and support of services.
5. **Continual Service Improvement (CSI)** – Ongoing improvement using metrics.

**Relationship with Agile:** Agile practices like CI/CD and DevOps accelerate Service Transition and Operation phases.

**Q52. What is regression testing and why is it important in the closing phase?**

**Regression Testing** (Unit-4):
- Re-running previously passed tests after code changes to ensure nothing is broken.
- Verifies that new changes have not introduced new defects.

**Why Important in Closing Phase:**
1. Final code fixes and patches may accidentally break existing functionality.
2. Ensures the system is stable before delivery.
3. Provides confidence to both developers and clients.
4. Automated regression suites (via CI) run quickly and repeatedly.

**Example:** After fixing a payment bug, regression tests verify that the login, cart and order modules still work correctly.

Types: Full regression, partial regression, smoke testing (sanity check).

## Unit 5: Scrum Methodology (Q53–Q60)

**Q53. Explain the Scrum artefacts and their purpose.**

**Three Scrum Artefacts** (Unit-5):

1. **Product Backlog:**
   - Ordered list of all desired features, enhancements and fixes.
   - Owned and managed by Product Owner.
   - Continuously refined (backlog grooming).

2. **Sprint Backlog:**
   - Subset of product backlog selected for the current sprint.
   - Owned by Development Team.
   - Updated daily.

3. **Increment:**
   - The sum of all completed product backlog items at the end of a sprint.
   - Must meet the Definition of Done.
   - Potentially shippable product.

Each artefact provides transparency and enables inspection and adaptation.

**Q54. Explain the five Scrum events (ceremonies) and their time-boxes.**

**Five Scrum Events** (Unit-5):

| Event | Purpose | Time-box |
|---|---|---|
| Sprint | Container for all other events | 1–4 weeks |
| Sprint Planning | Plan the sprint goal and backlog | Max 8 hours (4-week sprint) |
| Daily Scrum | Inspect progress, plan next 24 hours | 15 minutes |
| Sprint Review | Demo increment to stakeholders | Max 4 hours |
| Sprint Retrospective | Inspect process, plan improvements | Max 3 hours |

Time-boxing ensures focus, discipline and prevents meeting overruns.

**Q55. What is the Definition of Done (DoD) in Scrum and why is it important?**

**Definition of Done (DoD)** (Unit-5):
- A shared, explicit agreement within the Scrum team on what it means for a product backlog item to be complete.

**Typical DoD includes:**
- Code written and peer-reviewed.
- Unit tests written and passing.
- Integration tests passing.
- Code committed to repository (GitHub).
- Documentation updated.
- No known critical defects.
- Deployed to staging environment.

**Importance:**
1. Creates shared understanding and prevents ambiguity.
2. Ensures consistent quality across all increments.
3. Prevents technical debt accumulation.
4. Provides transparency to stakeholders about what "done" really means.

**Q56. Explain Test-Driven Development (TDD) in XP and its benefits.**

**Test-Driven Development (TDD)** (Unit-5 – XP Practice):
- Development approach where tests are written before the actual code.

**TDD Cycle (Red-Green-Refactor):**
1. **Red** – Write a failing test (feature does not exist yet).
2. **Green** – Write minimum code to make the test pass.
3. **Refactor** – Clean up code while keeping tests green.

**Benefits:**
1. Catches defects early (before integration).
2. Acts as living documentation.
3. Encourages modular, testable code design.
4. Reduces debugging time.
5. Increases developer confidence when making changes.
6. Naturally supports Continuous Integration.

TDD is a core XP practice that integrates well with Scrum sprints.

**Q57. What is the Scrum of Scrums and how does it scale Scrum for large projects?**

**Scrum of Scrums** (Unit-5 – Scrum Scaling):
- A technique to coordinate multiple Scrum teams working on the same product.

**How it Works:**
- Each Scrum team sends a representative (usually the Scrum Master or senior developer).
- Representatives meet regularly (daily or weekly) — the "Scrum of Scrums" meeting.
- Discusses: What did your team do? What will they do? Any cross-team impediments?

**Purpose:**
1. Coordinates dependencies between teams.
2. Resolves cross-team impediments.
3. Ensures alignment on shared goals.

**Other Scaling Frameworks:**
- **SAFe** (Scaled Agile Framework) – Enterprise-level.
- **LeSS** (Large Scale Scrum) – Minimal structure.
- **Nexus** – Scrum-based scaling framework.

**Q58. Explain Continuous Delivery (CD) and how it differs from Continuous Integration (CI).**

Both are DevOps/XP practices used in Scrum (Unit-5):

**Continuous Integration (CI):**
- Developers frequently merge code into a shared repository (multiple times per day).
- Automated build and test pipeline runs on every merge.
- Goal: Detect integration errors quickly.
- Example: GitHub Actions running unit tests on every pull request.

**Continuous Delivery (CD):**
- Extension of CI where every code change that passes tests is automatically prepared for release.
- Code is always in a deployable state.
- Human approval needed before production deployment.

**Continuous Deployment:**
- Fully automated — every passing change is automatically deployed to production.
- No human approval step.

| Practice | Automation Level | Human Approval |
|---|---|---|
| CI | Build + Test | Not required |
| Continuous Delivery | Build + Test + Stage | Required for production |
| Continuous Deployment | Build + Test + Deploy | None |

**Q59. What is technical debt in software projects? How does XP/Scrum help manage it?**

**Technical Debt** (Unit-5):
- The implied cost of future rework caused by choosing a quick/easy solution now instead of a better, longer-term approach.
- Accumulates when code quality is sacrificed for speed.

**Causes:**
- Skipping code reviews.
- No unit tests.
- Copy-paste programming.
- Ignoring refactoring.

**How XP/Scrum Manages Technical Debt:**

| Practice | How it Reduces Debt |
|---|---|
| Pair Programming | Immediate code review prevents bad code |
| TDD | Forces testable, clean code |
| Refactoring | Continuously improves code quality |
| Coding Standards | Consistent, readable code |
| Definition of Done | Prevents incomplete work being declared done |
| Sprint Retrospective | Team identifies and plans debt reduction |

Left unmanaged, technical debt slows future development and increases defect rates.

**Q60. Compare Waterfall, Scrum and XP methodologies across key parameters.**

Comprehensive comparison (Units 3, 4 & 5):

| Parameter | Waterfall | Scrum | XP (Extreme Programming) |
|---|---|---|---|
| Approach | Sequential | Iterative/Incremental | Iterative/Incremental |
| Flexibility | Low – changes costly | Medium – changes between sprints | High – welcomes change anytime |
| Delivery | Single final delivery | Working software every sprint | Frequent small releases (weekly) |
| Customer Involvement | Low (mainly at start/end) | High (Product Owner daily) | Very high (on-site customer) |
| Testing | End of project | Throughout sprints | Continuous (TDD) |
| Documentation | Heavy | Minimal | Very minimal |
| Team Size | Any | Small (5–9 members) | Small (2–12 members) |
| Key Strength | Clear structure, easy to manage | Flexibility, transparency | Engineering quality, speed |
| Key Weakness | Rigid, late defect detection | Needs experienced team | Difficult to scale |
| Risk Management | RMMM plan | Sprint Reviews, Retrospectives | Continuous feedback loops |

Understanding these differences helps choose the right methodology based on project type, size and requirements stability.
