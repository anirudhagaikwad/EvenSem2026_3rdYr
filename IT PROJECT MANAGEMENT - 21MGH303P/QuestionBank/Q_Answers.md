**1. Discuss various cost controlling techniques used in project monitoring.**  
Cost controlling techniques help keep the project within the approved budget.  
Step-by-step:  
1. **Earned Value Management (EVM)** – Compare Planned Value (PV), Earned Value (EV) and Actual Cost (AC).  
2. **Cost Performance Index (CPI)** = EV / AC → If CPI < 1, corrective action is needed.  
3. **Cost Variance (CV)** = EV – AC → Negative variance triggers control.  
4. **Budget at Completion (BAC) forecasting** using Estimate at Completion (EAC = BAC / CPI).  
5. **Cost Change Control System** – Formal approval for any cost change.  
6. **Resource levelling and optimisation** to reduce unnecessary expenses.  
7. **Regular cost audits and variance analysis** at every milestone.  
These techniques ensure proactive cost control in Unit-3 monitoring phase.

**2. Explain project risk management and mitigation strategies with suitable examples.**  
Project risk management is a systematic process (Unit-3).  
Steps:  
1. **Risk Identification** – Brainstorming, checklists, SWOT.  
2. **Risk Analysis** – Qualitative (probability-impact matrix) & Quantitative (Monte Carlo simulation).  
3. **Risk Response Strategies (Mitigation):**  
   - **Avoid** – Eliminate risk (e.g., change vendor).  
   - **Mitigate** – Reduce impact (e.g., add buffer time).  
   - **Transfer** – Insurance or outsourcing.  
   - **Accept** – For low-impact risks.  
Example: In software project, risk of delay due to team skill gap → Mitigation: Conduct training (mitigate) or hire expert (transfer).  
4. **Risk Monitoring** – Continuous tracking using risk register.  
This forms the core of RMMM plan.

**3. Describe the role of configuration management, GitHub and unit testing in project monitoring.**  
Configuration Management (CM) maintains integrity of project deliverables (Unit-3 practical).

- **GitHub** – Acts as SCM tool: Version control, branching, pull requests, issue tracking.

1. Baseline creation → GitHub repo.  
2. Change requests → Reviewed via pull request.  
3. Unit tests written & executed automatically (CI).  
4. Any failure triggers immediate corrective action.  
Thus, CM + GitHub + unit testing prevent scope creep and maintain quality during monitoring.

**4. Explain how to analyze cost and schedule performance index for project monitoring.**  
Cost and Schedule Performance Index (EVM – Unit-3).  
Formulas:  
- **CPI** = EV / AC  
- **SPI** = EV / PV  

Step-by-step analysis:  
1. Collect PV, EV, AC at review point.  
2. Calculate CPI & SPI.  
3. Interpretation:  
   - CPI > 1 → Under budget; CPI < 1 → Over budget.  
   - SPI > 1 → Ahead of schedule; SPI < 1 → Behind schedule.  
4. Forecast EAC & ETC.  
5. Take corrective actions (crashing, fast-tracking, resource reallocation).  
Example: CPI = 0.9 & SPI = 0.85 → Project is over budget and behind schedule → Immediate controlling techniques required.

**11. Describe the Agile Manifesto, its principles and key practices.**  
**Agile Manifesto (2001):**  
- Individuals & interactions **over** processes & tools  
- Working software **over** comprehensive documentation  
- Customer collaboration **over** contract negotiation  
- Responding to change **over** following a plan  

**12 Principles:** Customer satisfaction, welcome change, frequent delivery, daily collaboration, motivated individuals, face-to-face communication, working software as progress measure, sustainable pace, technical excellence, simplicity, self-organising teams, regular reflection.

**20. A software project has PV = ₹10,00,000, EV = ₹8,50,000 and AC = ₹9,00,000. Compute CPI and SPI and suggest improvements.**  
**Calculations:**  
- **CPI** = EV / AC = 8,50,000 / 9,00,000 = **0.944** (Over budget)  
- **SPI** = EV / PV = 8,50,000 / 10,00,000 = **0.85** (Behind schedule)  

**Suggestions:**  
1. Reallocate resources to critical path.  
2. Apply crashing on high-impact tasks.  
3. Conduct risk review & activate mitigation.  
4. Reduce non-value-adding scope (with stakeholder approval).  
5. Improve team productivity through training.

**30. Explain limitations of Scrum framework.**  
**Limitations** (Unit-5):  
1. Not suitable for very large projects without scaling frameworks (SAFe, LeSS).  
2. Requires high discipline and experienced team.  
3. Less documentation may cause issues in regulated industries.  
4. Scope creep if Product Owner is not strong.  
5. Daily meetings can become time-consuming if not time-boxed.  
6. Difficult for fixed-price/fixed-scope contracts.
